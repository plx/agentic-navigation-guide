# Agentic Navigation Guide v0.2 Contract

## Status and authority

This document is the normative target for the v0.2 guide language, its mapping
to filesystem entries, its filesystem trust boundary, and its supported
product/API boundary. It is maintained user documentation. The language and
representation decision is tracked by
[#34](https://github.com/plx/agentic-navigation-guide/issues/34); the trust,
containment, guide-input, and output-path decision is tracked by
[#35](https://github.com/plx/agentic-navigation-guide/issues/35); and the
CLI-only product/API decision is tracked by
[#36](https://github.com/plx/agentic-navigation-guide/issues/36).

The current `0.1.4` implementation does not yet conform to every rule in this
document. Known grammar and operation differences record exact current results
in the executable conformance ledger. The trust decision uses a separate
machine-readable policy/handoff ledger; its focused owners add red-before-fix
behavioral gates. The API decision uses an exact current-export disposition
ledger; its focused owners remove or privatize that migration surface. Every
difference is assigned in
[Implementation handoff](#implementation-handoff). The current implementation
does not silently override this contract.

Later production-readiness work will extend this same document with the full
CLI, security, and platform contracts while preserving the CLI-only API
boundary. It must not create a competing normative specification. `README.md`
remains the concise user entry point. `Specification.md` is historical design
input and is not normative.

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, MAY, and OPTIONAL in this document are to be interpreted as
described in RFC 2119 and RFC 8174 when, and only when, they appear in all
capitals.

## Contract boundary

This document decides:

- how a guide block is recognized and parsed;
- which filesystem names and entry types the guide can represent;
- how a represented item maps to filesystem identity;
- how `dump` and `init` serialize supported entries;
- the meaning of choices, comments, placeholders, and `ignore=true`;
- whether a listing is partial or exhaustive;
- how empty input and empty generated output behave; and
- how exclusion patterns match;
- which guide and root paths are trusted or implicit;
- how links, containment, diagnostics, and filesystem output are handled; and
- the stable-filesystem boundary for v0.2;
- that the installed CLI is the sole supported v0.2 product; and
- the current Rust export dispositions and `0.2.x` compatibility policy.

CLI options named here are binding only where they expose these grammar and
filesystem decisions. Issue #67 owns the complete command and option contract.

There is no supported Rust entry point in v0.2. The CLI's internal paths MUST
implement the same language, `ignore`, guide-input, containment, and diagnostic
outcomes defined here.

## Core invariant

For a supported, stable filesystem tree, successful generation and
verification MUST preserve filesystem identity:

```text
filesystem tree
  -> serialize with dump or init
  -> parse and check
  -> verify against the same tree
  = success for the same names, hierarchy, and regular-file/directory types
```

The invariant is about the represented tree. It does not promise
byte-for-byte preservation of Markdown prologue or epilogue text, comments,
choice shorthand, insignificant layout, or line-ending style.

Traversal, classification, validation, and serialization are all-or-nothing.
If one included entry is not representable, generation MUST fail before
delivery begins; it MUST NOT knowingly emit or write a plausible partial
guide. Filesystem destination guarantees are defined in
[Filesystem output destinations](#filesystem-output-destinations). Arbitrary
stdout delivery remains fallible and cannot be rolled back.

`dump --omit-xml-wrapper` emits only a nonempty active-body fragment for
embedding. The fragment is not independently checkable, but placing it between
the exact active opening and closing lines MUST produce the same checkable
document that ordinary `dump` would emit.

## Document and marker grammar

A guide document is UTF-8 Markdown containing exactly one guide block.
Prologue and epilogue text MAY surround the block.

The following grammar uses `SP` for U+0020 SPACE, `HTAB` for U+0009,
`BACKSLASH` for U+005C, `LF` for U+000A, and `CRLF` for U+000D U+000A.

```text
document             = prologue (active-block / ignored-block) epilogue
prologue             = *(markdown-line line-ending)
epilogue             = *(line-ending markdown-line) [line-ending]
active-block         = active-opening-line line-ending body
                       line-ending closing-line
ignored-block        = ignored-opening-line line-ending
                       *(opaque-line line-ending) closing-line
active-opening-line  = outer-ows "<agentic-navigation-guide>" outer-ows
ignored-opening-line = outer-ows "<agentic-navigation-guide" rws
                       ignore-attribute ows ">" outer-ows
ignore-attribute     = "ignore" ows "=" ows
                       ("true" / DQUOTE "true" DQUOTE)
closing-line         = outer-ows "</agentic-navigation-guide>" outer-ows
outer-ows            = *WSP
ows                  = *WSP
rws                  = 1*WSP
WSP                  = SP / HTAB
line-ending          = LF / CRLF
markdown-line        = *non-line-ending, excluding a marker candidate
opaque-line          = *non-line-ending, excluding a marker candidate
non-line-ending      = any Unicode scalar except CR / LF
DQUOTE               = U+0022
```

`outer-ows` is used only outside marker markup. `ows` is the shared optional
horizontal-whitespace production used inside attributed markers and around
choice alternatives; the two deliberately share the same lexical definition.

Every marker occupies its own complete line. The ignored-block production
permits zero opaque lines. “Excluding a marker candidate” means the candidate
scan described below runs before a line can be treated as Markdown or opaque
body text.

Marker rules are:

- The marker name is case-sensitive.
- Bare opening marker markup is exactly `<agentic-navigation-guide>`.
- The only attribute is one `ignore` attribute whose only value is `true`.
- Spaces or tabs MAY surround `=` in the attribute.
- An attributed marker requires at least one space or tab between the marker
  name and `ignore`.
- Unknown, duplicate, concatenated, valueless, false-valued, unquoted
  non-boolean, single-quoted, or malformed attributes are invalid.
- Whitespace between the marker name and `>` without an attribute is invalid.
- The closing marker has no attributes.
- Spaces or tabs MAY surround a complete marker on its line. No other text may
  share a marker line.
- CRLF and LF documents have identical meaning. A UTF-8 BOM is not part of a
  marker and is rejected if it precedes the opening marker on the same line.
- A lone CR is not a line ending and is invalid anywhere in the document.
- A second opening or closing marker line, including a nested block, is
  invalid.
- Text that merely contains a marker substring is ordinary prologue or
  epilogue text. After removing permitted outer horizontal whitespace, a line
  that starts with `<agentic-navigation-guide` or
  `</agentic-navigation-guide` is a marker candidate. A candidate that is not
  one of the productions above is malformed, not a different block name.

## Active body grammar

Unless `ignore=true` applies, the body MUST contain one or more entry lines.
It MUST NOT contain a blank line or other Markdown content.

```text
body              = entry-line *(line-ending entry-line)
entry-line        = indent "- " entry line-padding [comment]
indent            = *SP
entry             = placeholder / path-expression
placeholder       = "..."
line-padding      = *SP
comment           = "#" [SP] comment-text
comment-text      = *non-line-ending
```

After escape tokenization, `line-padding` consumes the maximal run of
unescaped U+0020 spaces immediately before a comment or the line ending. An
unquoted trailing space is therefore layout, not part of a path; a path with
edge spaces MUST use quoting.

The one space after `-` is syntax. A tab or a second unescaped space in that
position is not part of the delimiter. A name that begins with a space MUST
use a quoted path.

The first unescaped `#` outside a whole quoted path begins the comment. A
quoted choice does not suppress this lexical rule: `#` inside a quoted choice
MUST still be written `\#`. Spaces immediately before the delimiter are
layout, not part of the name. Leading and trailing spaces or tabs in comment
text are discarded. An empty or horizontal-whitespace-only comment is
equivalent to no comment. After the first comment delimiter, `#`, quotes,
brackets, commas, and backslashes have no grammar meaning.

## Indentation and parentage

Indentation uses spaces only. Tabs are invalid.

The first entry MUST have zero indentation. The first indented entry sets the
positive indentation unit for that guide. The unit MUST be between 1 and 16
spaces inclusive. Every later indentation width MUST be an exact multiple of
that unit.

The logical depth MAY increase by at most one between physical entry lines.
When depth increases, the immediately preceding physical entry MUST denote one
directory. A parser MUST NOT search backward past a file, placeholder, or
another sibling to find a more convenient parent. Dedenting closes the deeper
parents. Re-indenting is valid only beneath the immediately preceding
directory at the new parent depth.

The maximum logical depth is 256, where root entries are at depth 0.
Implementations MUST use checked arithmetic and MUST reject a greater depth
rather than overflow, panic, or silently reinterpret it.

The executable contract test constructs the otherwise unwieldy boundary
examples: depth 256 is valid and depth 257 is invalid.

Source order is preserved. A choice line expands in choice order at the same
depth.

<!-- contract-case: indent-two-spaces -->
```text
<agentic-navigation-guide>
- src/
  - cli/
    - check.rs
  - lib.rs
- Cargo.toml
</agentic-navigation-guide>
```

Four spaces is also a valid indentation unit.

<!-- contract-case: indent-four-spaces -->
```text
<agentic-navigation-guide>
- src/
    - main.rs
</agentic-navigation-guide>
```

Sixteen spaces is the largest valid indentation unit.

<!-- contract-case: indent-sixteen-spaces -->
```text
<agentic-navigation-guide>
- src/
                - main.rs
</agentic-navigation-guide>
```

Seventeen spaces is invalid.

<!-- contract-case: indent-seventeen-spaces -->
```text
<agentic-navigation-guide>
- src/
                 - main.rs
</agentic-navigation-guide>
```

The apparent child of `b` is invalid; it is not a child of `a`.

<!-- contract-case: indent-child-under-file -->
```text
<agentic-navigation-guide>
- a/
- b
  - c
</agentic-navigation-guide>
```

Skipping a logical depth is invalid.

<!-- contract-case: indent-skipped-depth -->
```text
<agentic-navigation-guide>
- a/
  - b/
      - c
</agentic-navigation-guide>
```

Tabs are invalid indentation.

<!-- contract-case: indent-tab -->
```text
<agentic-navigation-guide>
- src/
	- main.rs
</agentic-navigation-guide>
```

## Path expressions

A path expression represents either one regular file or one directory.
Directory expressions end with exactly one unescaped `/`. Regular-file
expressions do not.

The guide separator is `/` on every operating system. Each entry is relative
to its textual parent. A path MAY contain multiple components, so
`src/cli/main.rs` is one valid file entry relative to the current parent.

Every decoded path component:

- MUST be nonempty;
- MUST NOT be `.` or `..`;
- MUST NOT contain `/`, NUL, CR, LF, HTAB, another C0 control, or DEL;
- MUST be valid UTF-8;
- MUST preserve its Unicode scalar values without normalization.

The decoded whole path is rejected on every host if its first character is
`/` or `\`, or if its first component begins with an ASCII letter followed by
`:`, regardless of what follows. This rejects POSIX roots, Windows
root-relative paths, UNC/device forms, and drive-relative or drive-absolute
forms. A backslash elsewhere is a literal component character on hosts that
permit it; `dir/C:notes` is likewise a relative path whose host may still
reject the second component.

Repeated separators create an empty component and are invalid. More than one
trailing separator is invalid before directory-marker removal.

Two lexical path forms are available:

1. A bare path, used for ordinary readable names and choices.
2. A whole quoted path, used for syntax-sensitive names, the reserved literal
   `...`, and leading or trailing spaces.

```text
path-expression   = bare-path / quoted-path
bare-path         = bare-fragment [choice-list bare-fragment] ["/"]
bare-fragment     = *(bare-character / bare-escape)
bare-character    = path-source-character except BACKSLASH / "#"
                    / "[" / "]" / DQUOTE / line-ending
bare-escape       = BACKSLASH ("#" / BACKSLASH / "[" / "]"
                    / "," / DQUOTE / SP)
quoted-path       = DQUOTE 1*quoted-path-char DQUOTE ["/"]
quoted-path-char  = quoted-plain / quoted-path-escape
quoted-path-escape = BACKSLASH (DQUOTE / BACKSLASH)
quoted-plain      = path-source-character except DQUOTE / BACKSLASH
                    / line-ending
path-source-character = any Unicode scalar except CR / LF
```

At least one decoded component character is required after optional choice
expansion. Lexically, `bare-character` excludes backslash, `#`, `[`, `]`,
double quote, and line endings. The decoded component rules then reject
controls. A double quote at the beginning of an expression starts a whole
quoted path; a literal leading quote therefore uses `\"` or the whole quoted
form. The semantic component rules are applied after escape decoding and
choice expansion.

Two entries MUST NOT decode to the same full guide path. This includes
duplicates created by choice expansion and duplicates written through
different hierarchy or escape spellings.

Within a quoted path, `\"` represents a literal quote and `\\` represents a
literal backslash. `#`, `[`, `]`, comma, and spaces are literal. `/` remains a
component separator; no supported filesystem permits a literal `/` within a
name. A quoted path cannot contain a choice list. The directory slash, when
present, is outside the closing quote.

A quoted path may contain internal component separators, but it MUST NOT begin
or end with `/` or contain `//`. Thus `"src/main.rs"` is a file path,
`"src"/` is a directory path, and `"src/"` is invalid.

In a bare path:

- `\#`, `\\`, `\[`, `\]`, `\,`, `\"`, and `\ ` decode to the escaped
  character;
- every other escape is invalid;
- an unescaped `#` starts the comment;
- an unescaped `[` starts the one permitted choice list;
- an unescaped `]` is invalid;
- comma is ordinary outside a choice list, while a quote is escaped or uses
  the whole quoted form;
- interior spaces are literal; and
- a leading or trailing space requires the whole quoted form.

The reserved component `...` MUST NOT appear in a bare path. When the entire
unquoted expression is exactly `...`, it is the placeholder. In every other
position a literal `...` component requires a whole quoted path: the root file
is `"..."`, the directory is `"..."/`, and a nested file is
`"src/.../file"`. Placeholder recognition occurs before path decoding and
cannot be triggered by a quoted path.

## Choice lists

A bare regular-file path MAY contain one choice list. A choice list is compact
syntax for two or more sibling regular-file entries. It cannot produce a
directory or placeholder and cannot own indented children.

```text
choice-list          = "[" alternative *("," alternative) "]"
alternative          = ows (quoted-choice / unquoted-choice) ows
unquoted-choice      = *(unquoted-choice-char / bare-escape)
unquoted-choice-char = bare-character except "," / "[" / "]" / DQUOTE
quoted-choice        = DQUOTE *quoted-choice-char DQUOTE
quoted-choice-char   = quoted-choice-plain / quoted-choice-escape
quoted-choice-escape = BACKSLASH (DQUOTE / BACKSLASH / "#")
quoted-choice-plain  = path-source-character except DQUOTE / BACKSLASH
                       / "#"
```

Choice rules are:

- There MUST be between 2 and 256 alternatives inclusive.
- An empty alternative is valid when at least one other alternative is
  nonempty.
- Expansions MUST be unique after decoding.
- Spaces and tabs around an unquoted alternative are layout and discarded.
- A literal leading or trailing space in an alternative MUST be escaped as
  `\ ` or preserved by double quotes.
- Double quotes preserve all enclosed spaces, commas, and brackets.
- Within double quotes, `\"`, `\\`, and `\#` are escapes. An unescaped quote
  ends the alternative.
- In an unquoted alternative, comma is a separator and the bare-path escapes
  apply.
- `#` follows the outer comment rule. It MUST be written `\#` when it belongs
  to an alternative, including inside quotes.
- Prefix, each decoded alternative, and suffix are concatenated, then the
  complete path is validated.
- Every expansion MUST have the same sequence of parent components. Choices
  may therefore produce sibling files such as `src[/main, /lib].rs`, but a
  choice such as `x[a/b, c/d]y` is invalid because its expansions have
  different parents.
- A second choice list, an unclosed list or quote, a dangling escape, all-empty
  alternatives, a duplicate expansion, or a directory result is invalid.
- The same comment is attached to every expansion.

The executable contract test generates the count boundary: 256 alternatives
are valid and 257 are invalid.

```text

</agentic-navigation-guide>
```

<!-- contract-case: choice-empty-alternative -->
```text

</agentic-navigation-guide>
```

Quoted whitespace is significant.

<!-- contract-case: choice-quoted-whitespace -->
```text

</agentic-navigation-guide>
```


## Placeholders and listing completeness

Guides are partial by default. Omitting an item is valid without a
placeholder. There is no implicit exhaustive mode.

An unquoted exact `...` is a placeholder at its current parent:

- It MAY appear at the root or beneath a directory.
- It MUST NOT have children.
- Two placeholders MUST NOT be adjacent.
- A placeholder without a comment requires at least one actual, unlisted
  immediate child in that parent directory.
- A placeholder with a meaningful comment MAY be used when there is no
  unlisted child, including in an empty directory, to describe future or
  intentionally abstract entries.
- Multiple nonadjacent placeholders in one parent are valid. They use the same
  one-snapshot set of immediate children.
- A placeholder does not change the partial-listing rule or make a directory
  exhaustive.

“Unlisted” uses the exact filesystem identity rule below. A multi-component
listed path mentions its first component in the current parent for placeholder
accounting. Any UTF-8-named immediate child can satisfy an asserting
placeholder, even when its entry type is not otherwise representable; the
placeholder does not assert that child's type. An undecodable sibling makes
the snapshot fail rather than being silently counted.

<!-- contract-case: placeholder-forms -->
```text
<agentic-navigation-guide>
- src/
  - ...
  - main.rs
  - ... # future modules
</agentic-navigation-guide>
```

Adjacent placeholders are invalid.

<!-- contract-case: placeholder-adjacent -->
```text
<agentic-navigation-guide>
- src/
  - ...
  - ... # future modules
</agentic-navigation-guide>
```

A placeholder cannot own a child.

<!-- contract-case: placeholder-child -->
```text
<agentic-navigation-guide>
- ...
  - child.txt
</agentic-navigation-guide>
```

## Ignored guides

`ignore=true` is an explicit, whole-body opt-out. The document envelope,
single-block rule, exact opening marker, exact attribute grammar, and exact
closing marker are always validated. If that envelope is valid:

- the global marker-candidate scan runs first, so an opening, closing, or
  malformed marker candidate inside the apparent body is not opaque text and
  remains an envelope error;
- the body is opaque UTF-8 text and MAY be empty;
- list, indentation, path, choice, placeholder, and filesystem checks are not
  performed;
- `check`, single-guide `verify`, and recursive `verify` return a distinct
  `ignored` outcome; there is no supported v0.2 library entry point;
- the process succeeds by default and emits an ignored diagnostic unless
  quiet mode suppresses ordinary diagnostics;
- recursive summaries count ignored guides separately from passed guides;
- an ignored guide counts as discovered for zero-discovery behavior but not as
  verified; and
- `check` and `verify`, including recursive verification, accept
  `--deny-ignored`; under that policy any ignored result makes the command
  nonzero while remaining categorized and counted as ignored.

CI and hook workflows MUST pass `--deny-ignored` when ignored guides are not
an allowed opt-out. Execution-mode flags do not silently alter the default
allow policy.

Quiet mode changes output only. It does not change the ignored outcome or exit
policy. A malformed opening marker can never activate ignore.

## Recursive discovery and empty searches

Recursive `verify` separates discovery from verification. Only a successfully
completed discovery that returns no matching entries is an absent search.
Invalid guide-name or exclusion configuration, an invalid or unreadable root,
a traversal error, an unsafe matching entry, or a failure after discovering a
guide is an error in its own category and MUST NOT be converted to absence.

The CLI aggregate fields have these meanings:

- `Total` and `Discovered` are both the number of guide entries returned by
  successful discovery;
- `Passed`, `Failed`, and `Ignored` categorize those discovered entries;
- `Absent` is `1` only when this one recursive search discovered zero entries,
  and is otherwise `0`. It is an aggregate outcome indicator, not a count of
  guide files presumed to be missing.

An ignored guide therefore contributes one to `Total`, `Discovered`, and
`Ignored`, contributes zero to `Passed`, `Failed`, and `Absent`, and does not
take the zero-discovery path.

By default an absent search:

- states that zero navigation guides were verified;
- identifies the selected guide name and root using control-safe rendering;
- recommends checking `--root`, `--guide-name`, and `--exclude`, and identifies
  `--allow-empty` as the only successful opt-out;
- reports `Total: 0, Discovered: 0, Passed: 0, Failed: 0, Ignored: 0,
  Absent: 1` on standard error, including in quiet mode; and
- exits `2` in post-tool-use mode and `1` in default, pre-commit, and GitHub
  Actions modes.

`--allow-empty` is a CLI-only flag that requires `--recursive`. There is no
environment, configuration, execution-mode, quiet-mode, name, root, or
exclusion default that enables it. After successful discovery returns zero
entries, the flag makes the command exit `0`; non-quiet modes report the same
zero aggregate as ordinary output on standard output, while quiet mode is
silent. It cannot suppress a discovery, traversal, unsafe-entry, parsing,
validation, or verification error.

Required CI verification MUST omit `--allow-empty`. The option is only for a
caller that intentionally makes the complete recursive search optional.

## Empty guides and generated output

An active empty or whitespace-only guide body is invalid.

`dump` and `init` MUST validate the entire included input before success:

- the root MUST exist and be a directory;
- at least one included, representable entry MUST remain after depth and
  exclusion rules;
- an empty directory and a fully excluded directory fail with an actionable
  empty-output error;
- a regular-file root, missing root, unreadable root, unsupported entry, or
  transient enumeration failure fails;
- a traversal, classification, validation, or serialization failure occurs
  before `dump` writes guide bytes or `init` creates its destination.

Once delivery begins, stdout may report a partial write failure. Filesystem
destinations use the create-new contract below; this contract does not claim
impossible rollback of an arbitrary I/O device.

Depth-limited and excluded generation is still a valid partial listing when at
least one supported entry remains.

For `dump` and `init`, `--indent` accepts 1 through 16 and defaults to 2.
`--depth` accepts 0 through 256, with 0 selecting only root children. When
`--depth` is explicit, deeper entries are outside the generated listing. When
it is omitted, generation MUST fail if an included tree would require a
logical depth greater than 256 rather than truncate it silently.

## Filesystem-name representation

The following decision table is exhaustive by rule. “Quoted” means the whole
quoted-path form above, not a lossy display escape.

| Name or syntax class | v0.2 outcome |
| --- | --- |
| Nonempty UTF-8 ordinary component | Represent exactly |
| Non-ASCII and emoji scalar values | Represent exactly; no normalization |
| Interior U+0020 spaces | Represent bare or quoted |
| Leading/trailing U+0020 spaces | Represent with a whole quoted path |
| `#`, `[`, `]` | Escape in bare form or use a quoted path |
| Backslash where the host permits it | `\\` in bare or quoted form |
| Comma | Literal outside choices; escape or quote inside a choice |
| Double quote | `\"` in bare or quoted form |
| Literal component `...` | Whole quoted path; bare `...` is a placeholder |
| `/` within a component | Reject; it is the guide separator and is forbidden by supported filesystems |
| Empty, `.`, or `..` component | Reject |
| Repeated separator | Reject |
| Whole path beginning `/` or decoded `\` | Reject on every host |
| First component beginning ASCII `[A-Za-z]:` | Reject on every host |
| Drive-looking or backslash-leading later component | Represent as a literal component where the host permits it |
| Host-reserved or host-forbidden name that otherwise meets this grammar | Represent and verify only on a host that enumerates the exact name; otherwise fail actionably |
| NUL, CR, LF, HTAB, other C0 controls, or DEL | Reject and use the escaped diagnostic form below |
| Non-UTF-8 filesystem name | Reject with undecodable bytes or code units preserved in a safely escaped diagnostic |
| Name that changes during enumeration | Fail the operation; do not omit silently |

Every diagnostic that includes a rejected name MUST use a reversible,
double-quoted representation and MUST NOT emit raw control characters:

- valid UTF-8 uses `\"`, `\\`, `\0`, `\t`, `\n`, and `\r`; other C0 controls
  and DEL use uppercase `\u{XXXX}`;
- a non-UTF-8 Unix name renders every raw byte as uppercase `\xNN`; and
- an ill-formed Windows name renders every UTF-16 code unit as uppercase
  `\u{XXXX}`.

The replacement character U+FFFD MUST NOT stand in for undecodable input.
Diagnostics MAY prefix this representation with a safely rendered parent
path, but MUST preserve the rejected component exactly.

The serializer MUST emit one of the documented forms and the parser MUST
recover the exact UTF-8 scalar sequence. It MUST NOT percent-encode, base64
encode, normalize, replace, trim, or lossily display a supported name.

Canonical generation emits a component bare only when it is not `...`, has no
leading or trailing space, and contains none of `#`, `\`, `[`, `]`, comma, or
double quote. Otherwise it emits one whole quoted component, escaping only
`"` and `\`; bare `...` is never emitted for a literal name. A directory
suffix remains outside the closing quote. Canonical generation emits one
immediate filesystem child per physical entry line and represents deeper
components through indentation, so its whole quoted path contains exactly one
component. Siblings are emitted in ascending UTF-8 byte order, regardless of
host enumeration order or entry type.

## Filesystem entry types

The v0.2 textual format represents regular files and directories only.

| Filesystem entry | Textual verification | `dump` / `init` |
| --- | --- | --- |
| Regular file | File entry, no trailing `/` | Represent |
| Directory | Directory entry, one trailing `/` | Represent and traverse |
| Hard-linked regular file | Regular file; inode identity is not encoded | Represent as regular file |
| File symlink | Must not satisfy a file entry | Reject without following |
| Directory symlink | Must not satisfy a directory entry | Reject without traversing |
| Dangling symlink | Unrepresentable | Reject without following |
| Symlink loop or chain | Unrepresentable | Reject without following |
| Windows junction or other reparse link | Unrepresentable | Reject without following |
| FIFO or named pipe | Unrepresentable | Reject |
| Unix-domain socket | Unrepresentable | Reject |
| Block/character device | Unrepresentable | Reject |
| Unknown or transient type | Fail closed | Fail before output |

An exclusion that prunes an entry before inclusion may omit it. An included
unsupported entry aborts generation. Guide-file links, explicit guide paths,
output destinations, containment, and concurrent mutation follow
[Filesystem trust and containment](#filesystem-trust-and-containment).

## Filesystem identity

Each decoded component is matched against the exact UTF-8 name returned by its
parent directory:

- comparison is case-sensitive on every host;
- comparison performs no Unicode normalization;
- host filesystem aliases do not change guide identity;
- `README.md` does not match `Readme.md`;
- precomposed and decomposed Unicode spellings do not match; and
- if a host lookup resolves a different spelling, verification reports an
  actionable identity mismatch instead of treating it as success.

The verifier snapshots each parent directory once per verification and uses
that same snapshot for listed lookup, type classification, and placeholder
mentioned/unmentioned accounting. If the host cannot distinguish two required
identities or enumeration is ambiguous, verification fails rather than
guessing.

An undecodable name encountered in a directory snapshot fails verification,
even when a partial guide does not list that sibling. Otherwise the verifier
could not prove exact listed-name or placeholder identity. A directory pruned
before enumeration is outside the snapshot.

This is a textual identity contract, not a promise that every supported
filesystem can create every pair of names.

## Filesystem trust and containment

### Threat model and supported guarantee

The minimum supported deployment is an untrusted repository on a trusted
developer or CI machine.

The repository tree, guide bytes, filesystem names, links, link targets, and
special entries are untrusted. The selected executable, operating system,
kernel, process credentials, command-line arguments, and configuration
environment are trusted. A caller that derives an argument or environment
value from untrusted data is responsible for validating that derivation before
invocation.

V0.2 provides a **stable-filesystem containment guarantee**. A supported input
tree does not change from trust-anchor resolution through the last read or
enumeration that depends on it. Under that precondition:

- an implicit or recursively discovered guide is not read outside its
  canonical trust anchor;
- a textual item is not satisfied by an entry outside its canonical
  verification root;
- a link or reparse entry below an anchor is not followed as a regular file or
  directory; and
- a filesystem destination does not overwrite or follow an existing entry.

The one required concurrent exception is the destination-leaf creator race.
Creation MUST be one exclusive operation so another creator that wins after
preflight is never overwritten.

An implementation MUST fail when it observes a disappearance, type change,
identity change, or other inconsistency. That detection is defense in depth,
not a hostile-mutation guarantee. V0.2 does not promise containment against a
process that can replace a root, ancestor, guide, or item while the command is
running. Such a guarantee would require reviewed handle-relative traversal and
open operations on every supported operating system.

The verifier is a consistency checker, **not a filesystem sandbox, access
control boundary, malware scanner, or safe way to execute an untrusted
process**. User and security documentation MUST preserve that limitation.

### Trust anchors and path provenance

An effective root MUST exist, be a readable directory, and be canonicalized
once before dependent traversal. A root selected by the trusted caller MAY
itself be a symlink, junction, reparse alias, or have such ancestors. The
canonical directory it names becomes the trust anchor. This root-level opt-in
does not authorize links encountered below the anchor.

The effective anchors and path authorities are:

| Surface | V0.2 anchor or authority |
| --- | --- |
| Every `check` invocation | Canonical current working directory is the comparison anchor; a default guide is beneath it, while an explicit path may grant external authority |
| Single `verify` without an explicit guide path | Canonical effective verification root; the default guide is resolved from that root, not an unrelated working directory |
| Recursive `verify` | Canonical search root |
| `dump` and `init` input traversal | Canonical generation root |
| `--guide` or `AGENTIC_NAVIGATION_GUIDE_PATH` | Explicit read authority for the selected stable path, including a regular file outside the verification root |
| `--output` | Explicit create authority for the selected stable destination, including a destination outside the generation root |

`--guide` and `AGENTIC_NAVIGATION_GUIDE_PATH` are equivalent explicit guide
configuration. A default path and a path derived only from a guide-name
selector are implicit.

`--guide-name` and `AGENTIC_NAVIGATION_GUIDE_NAME` select exactly one nonempty
filename component. The value MUST NOT be `.`, `..`, absolute, rooted,
prefixed, or contain `/` or `\`. It is never an arbitrary path. Invalid values
fail before discovery or a file read.

A path lexically beneath an effective root MUST be resolved component by
component from that anchor. Every descendant component used as a directory
MUST be a real directory and MUST NOT be a symlink, junction, mount-point
reparse alias, or unknown reparse entry. Canonical containment is still
checked; an in-root link target does not make the link acceptable.

“Lexically beneath” uses component-aware comparison before link resolution.
First make the caller-supplied root spelling and configured path absolute
relative to the current working directory. Remove redundant separators and `.`
components, but preserve every unresolved `..` component in both spellings;
canceling it before resolving a preceding link or reparse component can change
which directory the operating system names. The path is lexically beneath the
root only when the resulting path has the complete root spelling as an exact
component prefix and the remaining tail contains no root, prefix, or `..`
component. The tail is then anchor-relative. The root entry itself may resolve
as the caller-selected alias; every component in the tail receives the
below-anchor rules. A path that fails this comparison can receive external
authority only through an explicit path option; an implicit path MUST fail
closed.

For example, if the caller selects `/alias` and `/alias` resolves to `/real`,
then `/alias/sub/out` is beneath the selected root and `sub` cannot be a link.
The alternate spelling `/real/sub/out` is not beneath the caller-supplied
spelling; if passed as an explicit guide or output path, it is a separate
external-path grant. Default paths are constructed from the selected root
spelling and cannot acquire external authority this way.

The unresolved spelling rule also applies when the root itself contains a
parent component. If `/alias` resolves to `/real/child`, a selected root
spelled `/alias/..` canonicalizes to `/real`, while `/alias/../sub` has the
same complete root spelling plus the safe tail `sub`. The spelling `/etc/out`
does not acquire the `/` prefix produced by lexically canceling `/alias/..`;
it remains outside the selected root and is never remapped below `/real`.

An explicit guide or output path that is lexically outside the applicable
effective root grants access to its stable resolved ancestor chain. That is a
deliberate caller capability, not authority derived from repository contents.
Its final entry remains subject to the non-following guide or destination rule
below. A caller that does not trust an external ancestor chain MUST pass a
canonical path beneath a separately trusted directory.

### Guide-file input

All CLI paths and direct internal engine paths MUST use one shared safe-guide
opening policy. The historical `trust-guide-direct-library-path` fixture ID
remains an internal shared-opener/no-bypass regression after removal of the
source library target. No public path/root construction route exists in v0.2.
Discovery classification followed by an unrestricted path reopen is not
sufficient.

| Guide-file class | V0.2 outcome |
| --- | --- |
| Implicit regular file inside its anchor | Read |
| Recursively discovered regular file inside the search root | Read; verify relative to its real containing directory |
| Explicit regular file inside the verification root | Read |
| Explicit regular file outside the verification root | Read; the exact configured path is the opt-in |
| Hard-linked regular guide | Read as a regular file; inode provenance is not represented |
| Final file symlink, whether implicit, recursive, or explicit | Reject before reading, even when the target remains in-root |
| Relative or absolute out-of-root guide symlink | Reject before reading |
| Dangling guide link | Reject before reading |
| Guide link chain or loop | Reject the matching entry without resolving the chain |
| Windows guide junction, mount point, or other link-like reparse entry | Reject before reading |
| Directory, FIFO, socket, device, or unknown entry with the selected guide name | Reject without opening it as a guide |
| Link/reparse directory encountered below a recursive root | Do not traverse; if the entry itself matches the selected guide name, reject it |
| Matching unsafe guide entry pruned by an exclusion | Omit before inclusion; otherwise a matching unsafe entry is an error, not a zero-guide result |
| Caller-selected root alias | Canonicalize and accept as the anchor |
| Link/reparse ancestor below an anchor | Reject, even when the final file is regular or the resolved path remains in-root |
| Stable ancestor in an explicitly selected external path | Accept as part of the caller-granted external path authority; the final entry must still be a non-link regular file |

There is no v0.2 option that opts a final guide-file link into being followed.
A caller that trusts its target can name the regular target directly.

On Windows, an implicit guide name MUST exact-match an enumerated regular-file
directory entry before opening. Guide-name and explicit-guide configuration
MUST reject alternate data stream syntax, reserved DOS device aliases, named
pipe or device namespaces, and verbatim/device prefixes that do not identify
an ordinary directory entry. Explicit authority does not convert a device or
stream into a guide file.

Unless pruned before inclusion by an explicit exclusion, a dangling, looping,
special, or otherwise unsafe entry whose name matches the guide selector MUST
produce a typed nonzero unsafe-guide error. It MUST NOT be silently filtered
into “no guides found.” A truly absent match follows
[Recursive discovery and empty searches](#recursive-discovery-and-empty-searches).

Guide classification and opening occur under the stable-filesystem
precondition. Implementations SHOULD compare non-following metadata before the
open with metadata from the opened handle and fail on a detected identity or
type change. That comparison does not strengthen the stated concurrency
guarantee.

### Diagnostic confidentiality

No v0.2 CLI mode emits a raw guide source line. This applies to default,
quiet, verbose, pre-commit, post-tool-use, GitHub Actions, single-guide, and
recursive output, whether the guide was implicit or explicit. V0.2 has no
source-echo opt-in.

Diagnostics MAY include:

- a line and column or other bounded source location;
- a typed reason;
- a bounded, control-safe representation of the specific path or token needed
  to explain that reason;
- an implicit or recursive guide path relative to its trust anchor; and
- an explicit guide path exactly as configured by the caller, rendered
  control-safely.

Diagnostics MUST NOT include:

- unrelated guide, prologue, epilogue, or ignored-body text;
- a complete offending source line;
- bytes read through a rejected guide path;
- a link target or resolved external canonical path; or
- raw controls, terminal escapes, or lossy replacement characters.

Containment diagnostics identify the safe logical path and the fact that it
crossed the boundary. They do not print the resolved external target.
Verbose logging does not weaken these rules. The reversible safe-rendering
rules in [Filesystem-name representation](#filesystem-name-representation)
apply to every untrusted path component or content-derived fragment.

### Textual-item containment

The canonical verification root is the only namespace in which textual items
may be satisfied. In addition to the lexical rules and entry-type table
already fixed by this contract:

- each path component below the root is inspected without following a link;
- every intermediate component used for traversal is a real directory;
- the final component is a real regular file or directory of the textual
  type;
- a symlink, junction, link-like reparse point, dangling link, chain, or loop
  in any component rejects even when its canonical target remains in-root;
- an existing or nearest-existing canonical resolution that leaves the root
  rejects without exposing the resolved target;
- listed lookup, type classification, recursion, and placeholder enumeration
  use the same validated stable path and parent snapshot; and
- every CLI path and direct internal engine path shares these checks; the
  regression retained under the historical direct-library fixture ID proves
  the binary-private route cannot bypass them.

The caller-selected root itself may be an alias as described above. The
no-link rule starts below its canonical target.

Issue #42 owns non-following entry classification and the already assigned
listed-item operation rows. Issue #51 owns centralized containment and the
stable-versus-hostile mutation implementation. Neither ticket may weaken the
other boundary.

### Filesystem output destinations

`init` and `dump --output` share one create-new, no-clobber contract. V0.2 has
no force or overwrite mode.

Before delivery:

1. validate the destination path and its parent;
2. reject any existing final directory entry using non-following
   classification;
3. complete input traversal, classification, generation, and serialization;
   and
4. retain the complete bytes before creating the destination.

The destination parent MUST already exist and resolve to a writable directory.
The command does not create missing parent directories.

For a destination beneath the generation root, every ancestor below that root
MUST be a real directory and the canonical parent MUST remain within the root.
A link/reparse ancestor is rejected even when its target is in-root. A
destination outside the generation root is allowed only because `--output`
explicitly grants create authority to its stable resolved parent. The
component-prefix rule above determines which case applies when the generation
root itself is an alias.

On Windows, an output path MUST identify an ordinary filesystem directory
entry. Alternate data stream syntax, reserved DOS device aliases, named-pipe
or device namespaces, and unsupported verbatim/device prefixes reject before
creation. A successful open is validated as a new regular disk-file handle;
explicit external authority does not authorize a device, pipe, or named
stream.

At final creation:

- one exclusive create operation MUST fail if any entry exists at the final
  name;
- an existing regular file, hard-link name, directory, file or directory
  link, dangling link, link chain or loop, Windows reparse entry, FIFO,
  socket, device, or unknown entry is never opened, truncated, replaced, or
  followed;
- a link target outside the root is neither created nor modified;
- a competing creator that wins after preflight is never overwritten;
- the complete buffer is sent with `write_all`; any userspace buffer is
  flushed, and the handle is synchronized for data-error reporting before
  success; and
- no directory synchronization or crash-durable publication is promised.

After a create, write, flush, synchronization, or validation failure, the
command MUST attempt identity-safe cleanup of every artifact it created and
MUST return nonzero. If cleanup succeeds, no artifact remains. If cleanup
itself fails, the command returns a distinct cleanup-failed error and safely
identifies every known residual artifact; it MUST NOT report success or hide
the residue. Cleanup MUST never remove an entry whose identity cannot still be
shown to belong to the invocation. A hostile rename or identity replacement
during cleanup is outside the supported concurrency model and MUST NOT be
described as contained.

Success means that `write_all`, buffer flush where applicable, data
synchronization, and handle validation succeeded. The parent directory is not
synchronized, so survival across an immediate power loss or kernel failure is
not promised. V0.2 makes no crash-durability guarantee.

Exclusive creation is atomic only for ownership of the final name. V0.2 does
not promise atomic content publication: a concurrent reader may observe an
in-progress prefix between successful creation and completion. A reader that
requires publication atomicity must wait for command success.

An absent destination inside the generation root is not part of the generated
tree. A pre-existing destination fails before traversal rather than being
listed and then overwritten. Stdout is not a filesystem destination; its
broken-pipe, flush, and exit-status behavior is owned by #47.

### Cross-platform interpretation

The policy is operating-system independent; the mechanism is not:

- Unix implementations use non-following metadata and exclusive creation
  semantics and test relative/absolute links, chains, loops, FIFOs, sockets,
  and devices.
- macOS runs the same link/output cases and separately records APFS
  case/Unicode capabilities. A caller-selected root alias may be
  canonicalized before descendant checks.
- Windows implementations inspect reparse attributes and tags rather than
  treating `FileType::is_symlink()` as an exhaustive junction/reparse test.
  File and directory symlinks, junctions, mount points, dangling reparse
  entries, and ancestor reparse entries receive real behavioral coverage.

An unavailable link-creation privilege or filesystem capability is recorded
as unavailable evidence, not a passing security test. The supported platform
matrix in #55 MUST execute every invariant the platform claims.

### Decision rationale

The rejected alternatives are deliberate:

- Merely spelling `--guide link` is not unambiguous consent to follow a link
  that an untrusted checkout can replace. A separate link opt-in would add
  target-boundary and provenance complexity without enabling a use case that
  cannot name the trusted regular target directly.
- Source-line output is not required to identify a path and line number, and
  varying disclosure by execution mode or path provenance is easy to bypass.
  The universal no-source-line rule is therefore simpler and safer.
- Default overwrite or a `--force` path for `dump` would require a second
  destructive replacement contract and more complex race semantics. V0.2
  keeps both filesystem sinks create-only; stdout remains available when a
  caller intentionally delegates replacement policy to another tool.
- Hostile-mutation containment would require different handle-relative
  primitives and reparse controls across Unix and Windows. Canonicalize,
  inspect, and later reopen cannot honestly provide that guarantee, so v0.2
  chooses the stable-filesystem boundary explicitly rather than implying a
  sandbox.

## Command-line and environment configuration

Every supported setting resolves in the order **CLI > environment > built-in
default**. Environment values are defaults, not explicit command-line
arguments: they MUST NOT activate a CLI `requires` relation or conflict with an
otherwise valid explicit option. Genuine CLI-vs-CLI requirements and conflicts
remain usage errors.

| Environment variable | Scope | Higher-precedence CLI selection | Built-in fallback |
| --- | --- | --- | --- |
| `AGENTIC_NAVIGATION_GUIDE_PATH` | `check` and non-recursive `verify` | `--guide` | No explicit path; resolve an implicit guide name |
| `AGENTIC_NAVIGATION_GUIDE_ROOT` | `dump`, `init`, and every `verify` mode | `--root` | Current directory |
| `AGENTIC_NAVIGATION_GUIDE_NAME` | Implicit `check`, implicit single `verify`, and recursive `verify` | Explicit `--guide` selects a path instead; recursive `--guide-name` selects the name | `AGENTIC_NAVIGATION_GUIDE.md` |
| `AGENTIC_NAVIGATION_GUIDE_LOG_MODE` | Global: `quiet`, `default`, or `verbose` | `--quiet`, `--verbose`, or `--log-level` | `default` |
| `AGENTIC_NAVIGATION_GUIDE_EXECUTION_MODE` | Global: `default`, `post-tool-use`, `pre-commit-hook`, or `github-actions` | `--execution-mode` or an applicable execution convenience flag | `default` |

For `check` and non-recursive `verify`, an effective explicit guide path wins
over the name selector even when both come from the environment. Recursive
verification never consumes `AGENTIC_NAVIGATION_GUIDE_PATH`; it resolves only
its implicit filename. `AGENTIC_NAVIGATION_GUIDE_PATH`, like `--guide`, retains
explicit guide-file authority. `AGENTIC_NAVIGATION_GUIDE_NAME` and the built-in
name retain implicit single-filename authority beneath the applicable anchor.

An implementation MUST decide relevance and higher-precedence selection before
parsing a lower-precedence environment value. Invalid shadowed or irrelevant
values therefore have no effect. A selected path or root environment value
MUST be nonempty and remain an operating-system path without lossy conversion.
A selected name MUST be valid UTF-8 and satisfy the implicit single-component
name rules. Log and execution values use the exact case-sensitive strings in
the table.

Environment-default resolution rejects a selected empty path/root or invalid
name/mode before command work. Those configuration diagnostics identify the
variable and expected form but MUST NOT reproduce the value or control-bearing
content. Such a pre-execution configuration rejection is a usage error and MUST
exit `2`, irrespective of the requested execution mode. A nonempty path/root
has no additional validity claim at this layer; subsequent existence, access,
trust, and diagnostic behavior follows the applicable filesystem-input rules.
Static help documents variable names, scope, values, defaults, and precedence;
it MUST NOT interpolate live environment values.

## Exclusion patterns

`dump`, `init`, and recursive discovery share one exclusion matcher.

```text
pattern          = component *("/" component)
component        = "**" / segment-pattern
segment-pattern  = 1*segment-token
segment-token    = literal / "*" / "?" / class / glob-escape
glob-escape      = BACKSLASH (BACKSLASH / "*" / "?" / "[" / "]")
class            = "[" ["!"] class-member *class-member "]"
class-member     = class-char ["-" class-char]
class-char       = class-literal / BACKSLASH (BACKSLASH / "]" / "-")
```

`literal` is one Unicode scalar other than `/`, `\`, `*`, `?`, `[`, or `]`.
`class-literal` is one scalar other than `/`, `]`, `\`, or `-`. Inside a
class, the latter three characters are written `\]`, `\\`, and `\-`; `/`
cannot be matched. An initial `!` negates the class; elsewhere it is literal.
A range includes both endpoints by Unicode scalar value and its first endpoint
MUST NOT exceed its second.

- Match input is a UTF-8 root-relative path with `/` separators.
- Matching is case-sensitive and performs no Unicode normalization.
- A pattern without `/` is a basename glob applied to every path component at
  every depth. For example, `target` and `*.tmp` match nested basenames.
- A pattern containing `/` is matched against the complete root-relative path.
  It has no implicit leading `**/`.
- Every match consumes the complete basename or root-relative path; it is not
  a substring search.
- `*` matches zero or more Unicode scalars within one component, `?` matches
  exactly one, and neither crosses `/`.
- `**` matches zero or more complete path components. It is special only as a
  complete component; embedded or adjacent `**` in a segment is invalid.
- Character classes match one scalar. They support literal sets such as
  `[abc]`, inclusive ranges such as `[a-z]`, and leading-`!` negation such as
  `[!0-9]`.
- A leading dot has no special treatment.
- Multiple patterns form a union; there is no negation or re-inclusion.
- An empty pattern; leading or trailing `/`; repeated `/`; `.` or `..`
  components; malformed `**`; an empty, unterminated, or descending class;
  and an unknown or dangling escape are usage errors reported before
  traversal.
- A matched directory is pruned before its children are read.
- A matched file is omitted.
- A non-UTF-8 entry encountered before pruning cannot match this UTF-8
  language and fails actionably rather than being silently included or
  omitted.
- The default init exclusions `.git`, `.svn`, `.hg`, `.bzr`, `CVS`, and
  `_darcs` are basename exclusions and therefore apply at every depth unless
  `--include-vcs-directories` is used.
- `.gitignore` files are not interpreted.

Examples:

| Pattern | Matches | Does not match |
| --- | --- | --- |
| `target` | `target`, `project/target` | `targets` |
| `*.tmp` | `a.tmp`, `nested/a.tmp` | `a.tmp.keep` |
| `project/target` | exactly that root-relative path | `other/project/target` |
| `projects/*/target` | one component between | `projects/a/b/target` |
| `projects/**/target` | `projects/target`, `projects/a/b/target` | `projects/a/b/target/file` |

Exclusions can make generation empty; the empty-output rule then applies.

The installed `agentic-navigation-guide` executable is the sole supported

this decision. Adding a supported Rust library later requires a separately

The immutable published `0.1.4` artifact permanently contains its own

and does not remove internal link detection. The CLI continues to classify

constructor, parsed model, path-taking verifier, split discovery helper, or

proof.

This boundary was selected because the documented product and installation
flow are CLI-oriented, no Rust embedding example or dependency instructions
exist, and the audited library surface exposes internal models, mutable
fields, exhaustive errors, third-party errors, and low-level filesystem
routes. Those routes can disagree with or bypass the approved v0.2 contract.
No published reverse dependency was visible during the 2026-07-25 decision
audit, although that cannot rule out private consumers. The intentional
`0.2.0` break gives such consumers one explicit migration boundary instead of
stabilizing unsafe or incorrect behavior.

The following alternatives are rejected for v0.2:

- preserving the broad library audited at the decision snapshot;
- calling the current library unsupported while continuing to publish it;
- hiding or feature-gating the current public surface; and
- inventing a new minimal facade without a demonstrated embedding use case.

The last option may be reconsidered for `0.3.0`. It would require opaque
requests and results, non-exhaustive error categories, a distinct `Ignored`
outcome, the shared safe-guide opener, a packaged downstream consumer, and a
separate approved API baseline.

## Compatibility and migration from 0.1.x

The v0.2 language is intentionally stricter because a permissive parse can
produce false verification success.

Users migrating a 0.1.x guide should run the v0.2 `check` command and address
all reported errors. In particular:

- malformed marker prefixes, unknown attributes, duplicate attributes,
  `ignore=false`, and whitespace-only pseudo-attributes are now invalid;
- `ignore=true` skips the entire body consistently after strict envelope
  validation;
- children are attached only to their immediate textual directory parent;
- tabs are not indentation;
- repeated trailing separators are rejected before normalization;
- quoted choice whitespace is preserved;
- duplicate, all-empty, directory-producing, and one-alternative choices are
  rejected;
- syntax-sensitive or edge-space names use whole quoted paths;
- quoted `"..."` represents the literal filesystem name while bare `...`
  remains a placeholder;
- newline/control and non-UTF-8 names are rejected;
- listed symlinks and special entries are unsupported rather than treated as
  regular files;
- implicit, recursive, and explicit guide-file links are rejected before
  reading; an explicit regular guide may still be outside the verification
  root;
- guide-name configuration is one filename component and cannot escape its
  anchor;
- diagnostics no longer quote raw guide source lines or resolved external
  targets;
- `init` and `dump --output` create a new file only and never overwrite an
  existing destination;
- case and Unicode spelling must exactly match directory enumeration;
- nested basename exclusions now apply at every depth; and
- empty or fully excluded generation fails instead of emitting an invalid
  empty block.

Unlike `0.1.x`, recursive verification also fails when it discovers zero
guides. A deliberately optional search must pass `--allow-empty` explicitly;
required automation must not use that migration escape hatch.

There is no lossy automatic migration. `dump` or `init` may regenerate a guide
after unsupported entries are excluded or removed, and hand-written comments
must then be reapplied deliberately.
